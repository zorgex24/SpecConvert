# Задание: Windows-приложение для преобразования Excel-спецификаций

## 1. Цель

Разработать оконное приложение для Windows, предназначенное для преобразования старых Excel-файлов со спецификациями оборудования, изделий и материалов в унифицированную табличную форму.

Исходные Excel-файлы имеют сложное форматирование: объединенные ячейки, одна логическая позиция может занимать несколько физических строк Excel, а данные одной позиции могут быть распределены между несколькими строками.

Примеры исходных файлов:

- `Исходник 1.xlsx`
- `Исходник 2.xlsx`

Пример требуемого результата:

- `Целевая форма.xlsx`

Главный принцип преобразования:

> Каждое значение количества в исходной спецификации соответствует отдельной строке целевой таблицы.

То есть:

**1 запись с заполненной графой «Кол.» в исходном файле → 1 строка в результирующем файле.**

Количество физических строк и объединенных ячеек, занимаемых этой записью в исходном Excel, значения не имеет.

---

# 2. Технологии

Разработать приложение на:

- C#;
- .NET 10;
- WPF;
- архитектура MVVM;
- Visual Studio 2026.

Для работы с Excel использовать библиотеку, не требующую установленного Microsoft Excel.

Предпочтительно:

- ClosedXML;

Приложение должно работать локально, без подключения к Интернету.

`.xlsx`

# 4. Структура исходных файлов

В приложенных примерах используются следующие логические графы:

1. Поз.
2. Наименование и техническая характеристика
3. Тип, марка, обозначение документа, опросного листа
4. Код продукции
5. Поставщик
6. Ед. измерения
7. Кол.
8. Масса 1 ед., кг
9. Примечание

В исходных файлах эти графы не обязательно соответствуют одной физической колонке Excel.

Например, в приложенных файлах из-за сложной верстки начало логических граф расположено примерно в колонках:

- `E` — Поз.;
- `I` — Наименование;
- `AI` — Тип/марка;
- `AU` — Код продукции;
- `BB` — Поставщик;
- `BK` — Единица измерения;
- `BO` — Количество;
- `BS` — Масса;
- `BX` — Примечание.

Однако **не следует жестко привязывать алгоритм только к этим буквам колонок**.

Программа должна сначала найти строку заголовка таблицы и определить колонки по текстам заголовков.

Нужно учитывать объединенные ячейки.

---

# 5. Структура результата

Результирующий файл должен содержать обычную таблицу без сложной многострочной структуры.

Столбцы:

| Столбец | Наименование |
|---|---|
| A | Поз |
| B | Наименование и техническая характеристика |
| C | Тип, марка, обозначение документа, опросного листа |
| D | Код продукции |
| E | Поставщик |
| F | Ед. измерения |
| G | Кол. |
| H | Масса 1 ед., кг |
| I | Примечание |

За образец оформления и структуры использовать файл `Целевая форма.xlsx`.

Главное требование — корректность данных. Полное визуальное копирование форматирования шаблона не является приоритетом.

---

# 6. Основной алгоритм

## 6.1. Обработка книги

Последовательно обработать все листы исходной книги.

Для каждого листа:

1. найти таблицу спецификации;
2. определить расположение логических граф;
3. исключить основную надпись чертежа, штампы, служебные надписи и другие данные вне спецификации;
4. найти строки, относящиеся к спецификации;
5. сформировать логические позиции.

---

# 7. Ключевое правило определения строки результата

**Строка исходной спецификации, содержащая значение в графе «Кол.», является основной точкой создания строки результата.**

Для каждого заполненного значения `Кол.` должна быть создана отдельная строка результата.

Например, в `Исходник 2.xlsx` встречается конструкция примерно следующего вида:

```
3 Стойка металлическая
Рабочая документация ...

МШК1-10-100    шт.    13
МШК1-12-100    шт.    88
МШК1-12-120    шт.    85
...
```

Здесь должно быть создано несколько строк результата — по одной для каждого типоразмера с количеством.

Например:

```
Стойка металлическая | МШК1-10-100 | ... | шт. | 13
Стойка металлическая | МШК1-12-100 | ... | шт. | 88
Стойка металлическая | МШК1-12-120 | ... | шт. | 85
```

Нельзя считать весь визуальный блок одной строкой результата только потому, что он имеет один общий номер позиции.

---

# 8. Сбор многострочного текста

В исходном файле значение одной логической ячейки может быть разбито на несколько физических строк.

Например:

```
Блочный комплектный распределительный пункт
совмещенный с двухтрансформаторной подстанцией,
в ж/б оболочке, высокой заводской готовности,
индивидуальной разработки укомплектованная:
```

Это должно быть распознано как единый логический текст, если все строки относятся к одной позиции.

При формировании результата части текста необходимо:

1. объединить;
2. убрать лишние переводы строк;
3. убрать повторяющиеся пробелы;
4. сохранить смысловое разделение слов;
5. не склеивать слова без пробела.

Результат:

`Блочный комплектный распределительный пункт совмещенный с двухтрансформаторной подстанцией, в ж/б оболочке, высокой заводской готовности, индивидуальной разработки укомплектованная:`

Аналогичную обработку выполнять для:

- наименования;
- типа/марки;
- кода;
- поставщика;
- примечания.

---

# 9. Наследование данных

Важная особенность исходных спецификаций: данные могут быть указаны только один раз для группы строк.

Например:

```
Стойка металлическая

МШК1-10-100    шт.    13
МШК1-12-100           88
МШК1-12-120           85
```

В этом случае все три строки относятся к `Стойка металлическая`.

Если единица измерения очевидно относится ко всем исполнениям одной позиции, она также должна наследоваться.

Поэтому требуется реализовать понятие **текущего логического блока позиции**.

При встрече новой позиции запоминаются ее общие данные.

Последующие строки с количеством используют:

- собственные данные строки;
- данные непосредственно предшествующих строк этого блока;
- общие данные позиции,

если соответствующая графа в самой строке количества пустая.

При начале следующей позиции контекст предыдущей позиции должен быть сброшен.

---

# 10. Позиционные обозначения

В графе `Поз.` могут находиться значения:

- `1`;
- `2`;
- `РП`;
- `РУВН`;
- `ШУ1`;
- `Т1, Т2`;
- и т. п.

Позиция не обязательно является числом.

Хранить ее как строку.

Если одна исходная позиция содержит несколько строк с количеством, допустимо повторять исходное позиционное обозначение в каждой результирующей строке.

Например:

```
3 | Стойка металлическая | МШК1-10-100 | ... | 13
3 | Стойка металлическая | МШК1-12-100 | ... | 88
3 | Стойка металлическая | МШК1-12-120 | ... | 85
```

Не генерировать новую нумерацию вместо исходной.

---

# 11. Заголовки разделов

В исходных файлах присутствуют строки типа:

- `Оборудование`;
- `Изделия и материалы`;
- `Изделия и материалы (Изоляторы)`;
- `Материалы`.

Они не имеют количества и не являются обычными позициями.

Их необходимо переносить в результат как строки-разделители.

Для строки-разделителя:

- `Поз.` — пусто;
- `Наименование` — название раздела;
- остальные графы — пустые.

При этом строки-разделители должны сохранять правильное положение относительно позиций.

---

# 12. Отличие строки-разделителя от продолжения позиции

Необходимо предусмотреть отдельную логику распознавания.

Нельзя считать каждую строку без количества заголовком раздела.

Большинство строк без количества являются продолжением:

- наименования;
- типа;
- технической характеристики;
- примечания;
- другого поля позиции.

Поэтому заголовок раздела должен определяться отдельно.

На первом этапе допустимо использовать сочетание признаков:

- заполнено только поле наименования;
- отсутствуют позиция, количество, единица измерения, тип/марка и прочие предметные поля;
- строка расположена между группами позиций;
- текст соответствует характерной структуре заголовка.

Архитектура должна позволять позднее улучшить классификатор.

---

# 13. Количество

Количество может быть:

- целым;
- дробным.

Не преобразовывать количество в текст без необходимости.

В результате сохранять числовой тип Excel, если исходное значение является числом.

Например:

`1`

`2`

`13`

`391`

`12,5`

должны оставаться числами.

---

# 14. Масса

Массу также сохранять числом, если исходная ячейка содержит числовое значение.

Пустая масса остается пустой.

Не подставлять `0`.

---

# 15. Пустые значения

Если исходное значение действительно отсутствует, результирующая ячейка должна быть пустой.

Не записывать:

- `null`;
- `N/A`;
- `0`;
- `-`;

если этого не было в исходном документе.

---

# 16. Очистка Excel-текста

При чтении текста необходимо очищать технические последовательности, которые могут появляться после импорта Excel, например:

`_x000D_`

Также нормализовать:

- `\r`;
- `\n`;
- табуляцию;
- повторяющиеся пробелы.

Но не изменять содержимое технических обозначений.

Например:

`КПСнг(А)-FRHF 1х2х0,5`

должно остаться без смысловых изменений.

---

# 17. Формулы

Если в исходном файле значение количества или другого поля задано формулой, по возможности читать вычисленное значение.

Приложение не должно переносить формулу в результат, если достаточно итогового значения.

---

# 18. Объединенные ячейки

Исходные документы содержат большое количество объединенных ячеек.

Парсер должен корректно читать значение объединенного диапазона.

Нельзя предполагать, что значение существует физически в каждой ячейке диапазона.

Необходимо учитывать верхнюю левую ячейку merged range.

---

# 19. Границы таблицы

Необходимо исключать из обработки штамп чертежа.

В исходных файлах после спецификации присутствуют данные типа:

- `Изм.`;
- `Кол.уч.`;
- `Лист`;
- `№док.`;
- `Подп.`;
- `Дата`;
- `Разраб.`;
- `Гл. спец.`;
- `Нач. отд.`;
- `Н.контр.`;
- `ГИП`;
- название проекта;
- номер документа;
- `Формат А3`;
- `Инв. № подл.`;
- `Подпись и дата`;
- `Взам. инв. №`.

Эти данные **никогда не должны попадать в результат как позиции спецификации**.

---

# 20. Работа с несколькими листами

Спецификация может продолжаться на следующих листах Excel.

Все листы необходимо объединять в одну результирующую таблицу.

При переходе между листами:

- повторяющийся заголовок таблицы не переносить;
- штамп листа не переносить;
- продолжение позиции должно обрабатываться корректно;
- порядок исходных листов сохранять.

---

# 22. Архитектура парсера

Не помещать весь алгоритм в обработчик кнопки.

Разделить как минимум на следующие компоненты:

```text
Models
    SpecificationItem
    SpecificationSection
    ParseWarning

Services
    ExcelReader
    SpecificationParser
    SourceLayoutDetector
    CellValueResolver
    TextNormalizer
    ExcelExporter

ViewModels
    MainViewModel

Views
    MainWindow
```

Пример модели:

```csharp
public sealed class SpecificationItem
{
    public string? Position { get; set; }

    public string? Name { get; set; }

    public string? TypeMark { get; set; }

    public string? ProductCode { get; set; }

    public string? Supplier { get; set; }

    public string? Unit { get; set; }

    public decimal? Quantity { get; set; }

    public decimal? UnitWeightKg { get; set; }

    public string? Note { get; set; }
}
```

Для заголовков разделов лучше использовать отдельный тип записи либо поле типа:

```csharp
public enum SpecificationRowType
{
    Item,
    SectionHeader
}
```

# 23. SourceLayoutDetector

Создать отдельный сервис определения структуры исходного листа.

Он должен искать заголовки по тексту, а не только по фиксированным координатам.

Поддержать варианты написания:

- `Поз.`
- `Поз`
- `Наименование и техническая характеристика`
- `Тип, марка`
- `Код продукции`
- `Поставщик`
- `Ед. измерения`
- `Кол.`
- `Кол`
- `Масса 1 ед., кг`
- `Примечание`

Сравнение выполнять после нормализации:

- убрать переводы строк;
- убрать лишние пробелы;
- привести к одному регистру;
- убрать переносы внутри слов вроде `изме- рения`.

Результатом работы сервиса должна быть структура примерно:

```csharp
public sealed class SourceLayout
{
    public int PositionColumn { get; init; }
    public int NameColumn { get; init; }
    public int TypeMarkColumn { get; init; }
    public int ProductCodeColumn { get; init; }
    public int SupplierColumn { get; init; }
    public int UnitColumn { get; init; }
    public int QuantityColumn { get; init; }
    public int UnitWeightColumn { get; init; }
    public int NoteColumn { get; init; }

    public int HeaderRow { get; init; }
}
```

Если графа занимает объединенный диапазон, хранить при необходимости не только номер одной колонки, но и диапазон колонок.

---

# 24. Главное правило парсера

Алгоритм не должен строиться по принципу:

> одна строка Excel = одна позиция.

Это принципиально неверно для данных файлов.

Использовать модель:

> физические строки Excel → логические блоки → строки результата.

Главным признаком возникновения `SpecificationItem` является наличие значения в графе `Количество`.

---

# 25. Пример сложного случая

Исходник:

```text
Поз.  Наименование             Тип/марка            Ед.    Кол.

4     Комплект установки ОПН:  КС.ОПН-14.009

      - контактной сети         ОПН-3,3-КМ-1         шт.     9
      на металлической стойке

      - ВЛ 10 кВ               ОПН-10,0-КВМ-3       шт.     5
      на металлической стойке
```

Результат должен содержать **две строки**, потому что имеется два значения количества.

При этом в каждой строке должно быть достаточно информации, чтобы она была понятна без просмотра соседней строки.

То есть парсер должен учитывать общий контекст:

`Комплект установки ОПН`

и конкретное исполнение:

`контактной сети...`

или:

`ВЛ 10 кВ...`

---

# 26. Предупреждения

Если приложение обнаружило строку с количеством, но не смогло достоверно определить:

- наименование;
- единицу измерения;
- тип/марку;

оно **не должно молча отбрасывать строку**.

Строку необходимо добавить в результат и сформировать предупреждение.

Например:

```text
Лист2, строка 30:
обнаружено количество "4", но не определена единица измерения.
Возможно наследование от предыдущей строки.
```

Предупреждения отображать в интерфейсе.

---

# 27. Отладочная информация

Для каждой результирующей строки желательно внутренне хранить происхождение данных:

```csharp
SourceSheet
SourceRow
```

Например:

```text
Лист2 / строка 30
```

В итоговый Excel эти служебные поля выводить не нужно.

Они нужны для:

- диагностики;
- проверки парсера;
- отображения предупреждений;
- последующего улучшения алгоритма.

# 28. Экспорт

После преобразования пользователь выбирает путь сохранения.

Результат сохранять в `.xlsx`.

Первая строка:

```text
Поз | Наименование и техническая характеристика | Тип, марка, обозначение документа, опросного листа | Код продукции | Поставщик | Ед. измерения | Кол. | Масса 1 ед., кг | Примечание
```

Форматирование сделать аналогичным `Целевая форма.xlsx`:

- перенос текста;
- границы;
- вертикальное выравнивание;
- разумная ширина колонок;
- автоматическая/расчетная высота строк;
- числовой формат для количества и массы.

---

# 29. Валидация результата

После парсинга автоматически выполнять проверку.

Основное контрольное условие:

**Количество строк типа Item в результате должно соответствовать количеству найденных исходных записей с заполненной графой «Кол.».**

Исключения допускаются только для явно выявленных служебных данных вне таблицы.

В журнал выводить, например:

```text
Листов обработано: 7
Ячеек количества найдено: 84
Позиций сформировано: 84
Заголовков разделов: 5
Предупреждений: 3
```

Если:

```text
Ячеек количества найдено != Позиций сформировано
```

выводить ошибку проверки.

- количество найденных строк;

# 31. Обработка ошибок

Приложение не должно аварийно завершаться при:

- поврежденной книге;
- неизвестной структуре;
- отсутствии графы `Кол.`;
- пустом листе;
- нестандартном объединении ячеек;
- текстовом значении в количестве;
- невозможности сохранить файл;
- открытом выходном файле в Excel.

Пользователю показывать понятное сообщение.

# 32. Требования к расширяемости

Текущие два исходника являются примерами, а не единственными файлами, которые будут использоваться.

Поэтому алгоритм должен быть максимально независим от:

- конкретного количества листов;
- конкретного номера строки;
- абсолютных координат ячеек;
- размеров объединенных диапазонов;
- высоты строк;
- ширины колонок;
- форматирования.

При этом не нужно создавать универсальный AI/OCR-анализатор Excel.

Нужен детерминированный парсер спецификаций данного семейства документов.

Архитектура должна позволять позднее добавлять отдельные `SourceProfile` для существенно отличающихся старых форм.

# 34. Эталонный критерий

После преобразования исходных файлов необходимо вручную сопоставить несколько сложных фрагментов с результатом.

Особое внимание уделить случаям:

### Исходник 1

Многострочным позициям, где:

- позиционное обозначение находится в первой строке;
- наименование занимает несколько строк;
- тип/марка занимает несколько строк;
- количество находится не в первой физической строке позиции.

### Исходник 2

Позициям, где одна общая позиция содержит несколько типоразмеров.

Например одна `Стойка металлическая` может иметь несколько вариантов:

```text
МШК1-10-100
МШК1-12-100
МШК1-12-120
МШК1-14-100
...
```

Каждый вариант с собственным количеством должен стать самостоятельной строкой результата.

# 35. Критерии приемки

Приложение считается работоспособным, если:

1. открывает оба приложенных исходных файла;
2. самостоятельно определяет таблицы спецификаций;
3. обрабатывает все листы;
4. не переносит штампы;
5. сохраняет заголовки разделов;
6. правильно собирает многострочные значения;
7. создает отдельную строку на каждое значение количества;
8. правильно обрабатывает несколько исполнений одной общей позиции;
9. сохраняет числовые значения количества и массы;
10. показывает результат в DataGrid;
11. позволяет вручную исправить результат;
12. экспортирует результат в структуру `Целевая форма.xlsx`;
13. не теряет строки с количеством;
14. сообщает о неоднозначно распознанных данных.

# 37. Важное требование к Codex

Не пытаться сразу написать весь проект одним большим изменением.

Сначала:

1. исследовать приложенные Excel-файлы;
2. описать обнаруженные закономерности;
3. предложить внутреннюю модель преобразования;
4. только после этого реализовывать парсер;
5. после реализации прогнать его на обоих исходниках;
6. сравнить число найденных количеств с числом сформированных позиций;
7. исправить выявленные ошибки;
8. затем реализовать окончательный UI.

При неоднозначном случае предпочтительнее сохранить строку и выдать предупреждение, чем потерять данные.

Главный инвариант приложения:

> **Ни одна реальная позиция, имеющая количество в исходной спецификации, не должна быть потеряна при преобразовании.**
